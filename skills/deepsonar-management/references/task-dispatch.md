# 任务下发（task dispatch）

> 状态：as-built（管理 Skill 流程、可选结构化契约与派发准入）；真实模型质量收益未评测。
> 同步日期：2026-10-29

下发一个任务前，先把「要做什么」和「现在具备什么条件」分开写清楚。本文是管理 Agent 在创建、拆分、重新下发平台任务前必须执行的流程；
白盒/黑盒的具体前置条件见 [`whitebox-checklist.md`](whitebox-checklist.md) 与 [`blackbox-checklist.md`](blackbox-checklist.md)。

一次任务 = 一个画布（`tasks create <projectId> --title ... --content ...`）。`content` 是任务说明，不是执行凭据：
写全说明不等于具备执行条件，口头授权也不等于平台已授权（权限上限见 [`permissions.md`](permissions.md)）。

## 0. 请求到可提交说明：按顺序执行

本节是管理 Skill 必须执行的语义复核，不替代平台鉴权、冻结快照或 Verify；第 3、4 节另说明已接入 API 的可选结构化契约门禁。
只生成任务不等于获得执行授权；提交仍走当前调度器 schema 支持的既有接口。

1. **保留请求。** 提取用户期望的结果、指定项目/资产、禁止项和已有授权；把原话与自己的解释分开。简单请求不要求用户先写专业模板，也不把“检查”自动解释为生产写入测试。
2. **先读已有上下文。** 从当前明确项目和相关任务/Finding ID 开始，使用当前身份获准的项目元数据、资产、材料索引、任务摘要和证据元数据。先查索引再读相关正文；默认一页、至多 10 个相关摘要，再按缺口读取至多 3 份材料。按当前 schema 可用的分页/筛选收窄；不支持时记录覆盖不足，不猜参数、不全量加载历史。记录已读 ID/版本、来源、事实状态、未读范围和停止原因。仅在出现具体缺口且仍在权限/预算内时扩大读取；身份拒绝、跨项目或预算到限即停，不能以“补背景”为由扩权。
3. **选择目的和方式。** 按下表分别选择目的与方式，不将白盒等同静态、黑盒等同写入。必要准备、执行、观察与清理保持一条链；只有可独立交付且前置条件可独立满足才拆任务。
4. **处理关键缺口。** 先查可用授权上下文；仍缺且会改变目标、范围、授权或可执行性时，合并为最少的针对性问题，写明受影响的判据及可选路径。已知信息不重复询问。非阻断未知项留在说明中，并指定如何观察/报告。允许的独立工作可继续，但不得把用户要求的动态确认静默改成静态结论。
5. **生成说明。** 用下方精简模板输出完整 title/content（每个拆分任务独立自包含），把材料 ID、基线和限制展开，不能只输出检查表、代词或“同上”。凭据仅保留受治理引用；缺少必要引用的草稿不能作为就绪任务提交。
6. **统一复核再提交。** 用第 5 节复核目标与八项语义及证据支持，给出可执行/受限/阻塞、具体原因、受影响判据、下一步。现有授权已足够时不再例行索要确认；关键授权或用户目标选择未解决时不提交依赖该条件的任务。记录接口返回的 task/canvas ID 和真实结果；失败/结果未知不可声称已下发，先查询状态再决定是否重试。

### 目的与方式选择

| 输入事实 | 目的 | 说明中必须保留 |
| --- | --- | --- |
| 只有范围和“看看有没有问题” | 探索 | 覆盖入口、风险面、证据产出；不要求预先漏洞假设，不承诺一定找到漏洞 |
| 明确可检验主张 | 假设验证 | 主张、反例、成立/不成立/无法判断条件 |
| 已有发现和修复/版本变化 | 复测 | 原 Finding/证据、原复现链、新旧基线差异；旧结论不当成本轮结论 |
| 已有发现但证据不够 | 补证 | 缺哪条证据、补证范围、对原结论的影响；不扩大成全站重审 |
| 源码可读、无法构建或无动态环境 | 静态；动态要求保留为缺口 | 数据流、触发前提、定位；不能声称动态确认或无漏洞 |
| 环境/身份/动作授权及平台条件均满足 | 动态；有源码时可混合 | 基线、账号/租户/资源矩阵、完整状态链、清理和停止条件 |
| 只有生产只读权限 | 受限观察 | 仅获准读操作/已有材料；写入验证仍缺条件，不是“不适用” |
| 关键目标、授权或必要账号缺失 | 阻塞相应动作 | 最少补充问题及可独立开展的部分；不能借用其他身份 |

### 事实状态与缺口

`verified` 只用于有可追溯读结果/证据支持的具体事实（写来源、基线/时间及核验范围）；
`declared` 是用户/材料声明尚未核验；`missing` 是当前目标需要但不可用/未授权/未确认；
`not_applicable` 只用于所选任务确实不需要的条件，并写理由。声明授权与平台权限分别记录，互不替代。
即使引用元数据存在，也不能据此宣称凭据有效、目标可达、写入已获授权或 PoC 已成功。以上状态用于有来源的人可读说明；结构化 `task_contract.prerequisites` 不接受客户端 `verified`，管理 Agent 的语义复核也不能代替 Scheduler 的可信核验。

### 精简提交模板

以下是人可读说明模板，不是新增 API 字段。示例见 [完整输入→输出](task-dispatch-examples.md)。

```text
title: <目标 + 资产/基线>
content:
目标与目的：<探索/验证/复测/补证；期望回答及交付>
资产与基线：<项目、仓库/环境、版本；与部署的关系>
范围与排除：<模块/入口、身份/租户/资源；必要状态链；不做什么>
方式与前置条件：<静态/动态/混合/受限；verified/declared/missing/not_applicable + 来源/原因>
材料与引用：<源码/历史任务/Finding/Evidence ID；受治理凭据引用，不含秘密>
动作与限制：<允许/禁止、外联边界、清理、停止条件>
预算：<已有平台上限与本次工作上限；到限返回覆盖与缺口，不自行扩大>
交付与完成条件：<证据形式、覆盖、成立/不成立/无法判断；静态和动态分开>
复核：<可执行/受限/阻塞 + 依据；受影响条件；待补项/责任来源与下一步>
```

预算优先复用项目和用户已给上限；无已知数值时可提出更小的工作预算并明确为管理 Agent 的规划值，不能冒充平台配置或为达到目标提高权限。若预算决定任务是否可完成，先澄清或明确限制。

## 1. 每次下发都要明确的八件事

这些是语义要求，不规定 Markdown 标题、段落数量或字数。不知道的项写「未知」，不要补写成已确认。

| # | 项 | 说明 | 常见错误 |
| - | - | - | - |
| 1 | 目标与预期交付 | 要证明/排除什么，产出什么形态的结果 | 只写「审计一下」 |
| 2 | 目标资产 / 基线 | 仓库、URL、主机、环境、commit 或版本基线 | 只给项目名，不给具体基线 |
| 3 | 范围与排除项 | 允许触碰的边界，明确不做什么 | 把多个不相关目标塞进一个任务 |
| 4 | 待验证假设与依赖 | 探索的覆盖问题，或验证/复测的假设，及前置事实 | 「顺便看看有没有别的问题」 |
| 5 | 可用材料与工具 | 源码、文档、HAR、凭据**引用**（不写明文） | 把账号密码、token、cookie 写进 `content` |
| 6 | 权限与停止条件 | 已授权的动作、禁止动作、何时停 | 默认授权出网 / 默认授权写操作 |
| 7 | 证据要求与完成标准 | 什么算跑完、要留什么证据 | 只说「找出漏洞」，不说完成判据 |
| 8 | 预算 | 时间 / 资源上限，已有输出的复用策略 | 无上限，或与任务规模明显不匹配 |

## 2. 拆分依据

按**可独立验证的假设**、**共同的前置条件**、**预算**、**状态链**拆分，不按「凑够几个任务」拆。

- 一条必要状态链（例如「创建 → 保存 → 发布 → 触发」）必须留在同一个任务里；拆开会让中间态无人验证。
- 多个互不相关的目标应分开下发，并在各自说明里记录依赖关系（谁先跑、谁等谁的结论）。
- 按动作分别标明只读与写入授权；同一获准验证链的读取、写入、观察、清理不机械拆开。授权边界不同且可独立交付时才拆分。
- 拆完仍跑不完，提出收窄范围或分期方案；改变用户目标须明确处理，不静默删去关键完成条件。

## 3. 可选契约、共享模板与创建反馈

`POST /projects/:id/tasks` 保留 `title/content`，可另提交 `task_contract`。Web 的可选契约编辑器与管理 CLI `tasks create --task-contract @contract.json` 走相同 API。未提供契约时继续接受自由文本并返回 `task_contract_not_assessed`；这不等于完成了前置条件检查。

场景模板和版本的唯一机器来源是 [TaskContract](../../../packages/shared-types/src/task-contract.ts)；API/Web 复用此定义，CLI 传递同一契约，文档示例不构成另一套自动填值。契约必须声明 `schema_version: 1`、`template_id`（engineering/whitebox/blackbox/graybox）和 `template_version: 1`。共享 schema 严格拒绝未知字段/版本/类型和重复前置条件 ID；空白裁剪、集合排序/去重不分析原始需求。已提供契约时，objective/targets/scope/evidence/acceptance 缺少基本信息会在创建和派发阶段阻塞；其他补充提示返回 `task_contract_warnings`，每项含 `code/path/message/suggestion`。创建前已知安全阻塞返回 `409 task_contract_blocked` 与 `task_contract_blockers`，不创建任务。无阻塞时返回 201；不要因为 warning 重复创建。

Canvas 保存规范化契约和模板版本，Job 保存冻结契约用于执行提示；模板更新不改旧任务。预算字段用于规划与提醒，不替代平台运行预算。验收文本由创建者确认，模板建议不会自动变成已承诺结果。

## 4. 平台派发前的可信边界

创建时先用已解析的 Hub 运行镜像与收窄后的网络做兼容性检查；Chrome/ClickHouse 需要出网而契约禁止时，返回结构化 409，不创建 Canvas/Job。凭据 UUID 按小写标准化后去重，大小写不同不影响同一引用的授权判定。

Scheduler 在沙箱创建前再次核对当前项目网络策略、引用凭据的存在/启用/项目范围与冻结 Job 边界。客户端 `allowed_actions` 只是本次限制，不能授予写权限或出网。平台对 `allowed_actions` 与 `required_actions` 的并集核验；可选允许动作也不能跳过授权。显式契约任务的出网取当前项目规则、冻结 Job 网络与契约允许动作的交集；即使任务请求 `allow_egress: true`，也不能绕过当前项目规则。未选择 egress 的契约会冻结为禁止出网；旧的无契约任务保留原网络覆盖语义。`identity` 是待核验的目标租户/角色/资源声明；凭据存在不证明已登录目标，也不证明有目标写权限。前置条件只能声明 `declared/missing/not_applicable`，不能提交 `verified`。

当前没有通用目标身份/写授权/材料可达性的可信探测器：必要身份、write 或必需前置条件无法核验时拒绝依赖链，返回具体补充项。不会为了探测权限尝试未授权写入。只读任务可明确声明 read；需要目标外联时另声明 egress，仍受实际项目/Job 策略限制。无法安全自动拆分任意自由文本，因此阻塞整条契约依赖链；要保留只读价值，应另建明确范围的只读任务，不能把动态验证目标标成已完成。

这是一道任务准入门，不是对沙箱任意命令的细粒度读写授权器。未声明或与正文矛盾的动作需要人工审核；字段检查不证明所有模型行为安全，也不取代现有平台准入。

## 5. 派发前统一复核（当前管理 Agent 执行）

逐项核对第 1 节八项是否足以执行，而非仅检查字段非空；尤其核对用户目标未改变、事实有来源、缺失未伪装为不适用、必要状态链完整、预算和完成条件可判定。所有目的与方式使用同一尺度：

- **可执行**：目标所需条件有依据，动作处于已知授权和平台边界，完成条件可验证。
- **受限**：明确部分可以执行，但具体条件缺失影响部分结论；列出影响、保留原目标和待补动作，只下发已获授权且有独立价值的部分。
- **阻塞**：缺少目标身份、授权或必要材料/账号，不能完成核心判据；不提交执行任务，交付完整草稿、最少问题、条件补齐后的下一步。

以下核验仅在当前授权和读取预算内进行；不能为了核验可用性先执行未经授权的测试。

派发前只做必要、低风险的核验（不主动扩权、不主动外联）：

| 核验项 | 做法 | 不满足时 |
| - | - | - |
| 资产 / 仓库可访问、基线可确定 | 只读探测、`git ls-remote`、HEAD 查询 | 记为 `missing`，阻塞依赖基线的执行，先补可读基线并保留原目标 |
| 凭据引用可用、身份 / 租户匹配 | 先读引用元数据（不回读明文），身份/租户须另有可信证据；仅有元数据不能判匹配 | 记为 `missing`，不要改用别的账号「先跑起来」 |
| 构建 / 测试入口可用 | 检查声明的命令与镜像能力 | 说明验证限制，不伪造可执行条件 |
| 写入动作是否在授权内 | 对照项目策略与任务契约 | 阻塞写入；如有独立价值可提出受限观察，保留未满足的原目标 |
| 出网 / PoC server | 必须落在既有授权范围 | 需要但未授权则不启动，记为 `missing`；确实不需要才记 `not_applicable` |

## 6. 与运行时问题的边界

大输出导致的 Job 失败（例如 Pi RPC 单帧超限）属于运行时/取证层，由运行时修复与诊断负责，不靠「让 Agent 少输出」
的提示词兜底；任务下发只负责把范围、材料与完成标准写清楚。

维护流程时按 [场景验收](task-dispatch-acceptance.md) 记录覆盖与未覆盖；文档检查不证明模型输出质量或实际任务完成质量。

## 7. 工程任务契约示例

以下示例仅做本地只读检查。修改沙箱工作区文件/测试缓存可声明 `workspace_write`，仍需 Scheduler 当前授权；它不包含推送代码、发布或修改外部业务资产，后者应声明 `write` 并经目标授权核验。

```json
{
  "schema_version": 1,
  "template_id": "engineering",
  "template_version": 1,
  "objective": "分析测试失败原因并交付修复建议",
  "targets": ["已挂载的项目源码"],
  "scope": ["相关模块和失败测试"],
  "exclusions": ["不修改文件，不部署，不访问外部目标"],
  "stop_conditions": ["所需材料不可访问或超出预算时停止并说明限制"],
  "allowed_actions": ["read"],
  "required_actions": ["read"],
  "forbidden_actions": ["write", "egress"],
  "acceptance": ["列出复现前提、相关代码证据和建议；未复现时说明限制"],
  "evidence": ["源码位置和已有测试日志引用"],
  "budget": {"max_minutes": 30, "max_steps": 20}
}
```

不要把任务本身“寻找根因”误设为创建前必须已证明的前置条件。构建、运行测试可能写沙箱缓存，应按需声明 `workspace_write`；涉及外部业务副作用则还需 `write`，不能自动归类 read。

## 8. 失败后重新下发

先核对失败阶段、已有副作用与产物，再决定是否重新下发；`rerun-current` 会重新冻结配置，不能视为无副作用事务重试。

| 现象 | 重下发前需要确认 |
| --- | --- |
| `PI_RPC_MESSAGE_TOO_LARGE` | 输出路径已修复或有有效缓解；运行时修复归 #765，不机械原样重跑 |
| `ENOSPC` | 空间已恢复，产物完整性与副作用已对账 |
| OpenSandbox 500 | 诊断具体原因，不默认删除 sandbox |
| `40P01` | 确定失败事务和外部效果；事务重试不等于 Job 可重跑 |
| 429 | 区分临时限流与额度耗尽，遵守等待提示和预算 |
| 未提交完成回执 | 可能已完成或部分完成，先对账，不只补一句完成标准 |
| 401/403/scope | 区分过期凭据、错误身份、范围不匹配和禁止；补齐条件须真实授权，不自动提权 |

## 9. 通用任务标准与研究候选（#767 / #794 首片）

所有已提供的 task_contract 都检查 objective/targets/scope/evidence/acceptance 基本完整性。exclusions 可以为空，有声明则纳入候选判据。省略 outcome、选择 task_defined 或 bounty_submission 都不绕过通用门。仍接受无契约旧入口但返回 unassessed；这是迁移缺口，不代表该任务已达到统一标准，也不是删除已启用契约绕过检查的理由。

outcome 子对象可显式为 `{"mode":"task_defined"}`；只有用户要求按指定项目规则形成可提交成果时才选 bounty_submission。后者的 rules_status unknown 可开展补证观察，但不能提交 Finding；supplied 须提供规则快照。用户授权选定的 source.sha256 只是材料身份声明，不是官方规则或权限认证。详见[通用标准与研究候选](../../../docs/TASK_OUTCOME_ADMISSION.md)。

先 emit_fact 保存观察/Artifact/Evidence，再经现有 Job Control API 提交研究候选；管理 CLI 不代替 Agent 伪造控制事件。所有已提供契约的 emit_finding 需要如下 outcome_claim（占位符须替换为真实上下文，不可直接执行）：

outcome_claim:
