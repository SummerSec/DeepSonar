# 任务下发（task dispatch）

下发一个任务前，先把「要做什么」和「现在具备什么条件」分开写清楚。本文是 `tasks create` 的配套检查表；
白盒/黑盒的具体前置条件见 [`whitebox-checklist.md`](whitebox-checklist.md) 与 [`blackbox-checklist.md`](blackbox-checklist.md)。

一次任务 = 一个画布（`tasks create <projectId> --title ... --content ...`）。`content` 是任务说明，不是执行凭据：
写全说明不等于具备执行条件，口头授权也不等于平台已授权（权限上限见 [`permissions.md`](permissions.md)）。

## 1. 每次下发都要明确的八件事

这些是语义要求，不规定 Markdown 标题、段落数量或字数。不知道的项写「未知」，不要补写成已确认。

| # | 项 | 说明 | 常见错误 |
| - | - | - | - |
| 1 | 目标与预期交付 | 要证明/排除什么，产出什么形态的结果 | 只写「审计一下」 |
| 2 | 目标资产 / 基线 | 仓库、URL、主机、环境、commit 或版本基线 | 只给项目名，不给具体基线 |
| 3 | 范围与排除项 | 允许触碰的边界，明确不做什么 | 把多个不相关目标塞进一个任务 |
| 4 | 待验证假设与依赖 | 本次要检验的假设，及其依赖的前置事实 | 「顺便看看有没有别的问题」 |
| 5 | 可用材料与工具 | 源码、文档、HAR、凭据**引用**（不写明文） | 把账号密码、token、cookie 写进 `content` |
| 6 | 权限与停止条件 | 已授权的动作、禁止动作、何时停 | 默认授权出网 / 默认授权写操作 |
| 7 | 证据要求与完成标准 | 什么算跑完、要留什么证据 | 只说「找出漏洞」，不说完成判据 |
| 8 | 预算 | 时间 / 资源上限，已有输出的复用策略 | 无上限，或与任务规模明显不匹配 |

## 2. 拆分依据

按**可独立验证的假设**、**共同的前置条件**、**预算**、**状态链**拆分，不按「凑够几个任务」拆。

- 一条必要状态链（例如「创建 → 保存 → 发布 → 触发」）必须留在同一个任务里；拆开会让中间态无人验证。
- 多个互不相关的目标应分开下发，并在各自说明里记录依赖关系（谁先跑、谁等谁的结论）。
- 只读观察与获准的写入验证分属不同任务：授权不同、风险不同、完成标准不同。
- 拆完仍跑不完，优先收窄范围而不是提高预算。

## 3. 可选的任务契约（`task_contract`）

`content` 继续承担人可读的任务说明；结构化契约是**可选**补充，用于机器可读的范围、前置条件状态与完成标准。
字段命名与承载方式以 API / schema 评审为准（当前为设计草案，`schema_version` 随契约演进）。

设计草案字段：

- `schema_version`
- `template_id` / `template_version`（使用模板时）
- 任务模式：白盒 / 黑盒 / 灰盒 / 其他
- 目标与基线、范围与排除项
- 假设及依赖
- 所需材料与凭据**引用**
- 目标租户 / 角色 / 资源边界
- 允许动作、禁止动作、清理与停止条件
- 前置条件及其状态：`verified`（已核验）/ `declared`（声明但未核验）/ `missing`（缺失）/ `not_applicable`
- 证据要求、完成标准与预算

约束：

1. **契约只收窄，不放宽。** 项目策略、身份权限与用户明确授权是上限，契约不能扩大范围、增加凭据或授权外联。
2. **凭据不入契约。** 账号、密码、token、cookie 一律走既有凭据引用与受治理下发机制。
3. **模板版本随任务冻结。** 创建时记录采用的模板版本与解析后的契约快照；后续更新模板不得静默改变已创建任务。
4. **模板单一来源。** 模板定义在仓库内版本化，API 与 Web 复用同一来源，不在文档 / 数据库 / 前端各写一套。

## 4. 创建阶段

- 旧客户端不带契约时继续可用；**不因缺少某个 Markdown 标题返回 400**。
- 文案缺项、信息不足、声明未核验 → 返回结构化 warning（问题字段、原因、建议补充项），任务照常创建。
- 显式提交契约时按 `schema_version` 校验类型 / 枚举 / 结构；结构非法按既有 API 规范报错。
- **鉴权与范围约束不降级为 warning**：越权、跨项目、超出凭据边界一律拒绝。
- 不自动推断授权，不静默填入虚构账号或「已验证」状态。
- `kind=standard` 不被强制套安全审计模板；工程类任务保留原有用途。

## 5. 派发前

派发前只做必要、低风险的核验（不主动扩权、不主动外联）：

| 核验项 | 做法 | 不满足时 |
| - | - | - |
| 资产 / 仓库可访问、基线可确定 | 只读探测、`git ls-remote`、HEAD 查询 | 记为 `missing`，任务改为先补基线 |
| 凭据引用可用、身份 / 租户匹配 | 列出引用元数据（不回读明文） | 记为 `missing`，不要改用别的账号「先跑起来」 |
| 构建 / 测试入口可用 | 检查声明的命令与镜像能力 | 说明验证限制，不伪造可执行条件 |
| 写入动作是否在授权内 | 对照项目策略与任务契约 | 收窄为只读观察，或拆出独立的写入任务 |
| 出网 / PoC server | 必须落在既有授权范围 | 未授权则不启动，记为 `not_applicable` |

## 6. 与运行时问题的边界

大输出导致的 Job 失败（例如 Pi RPC 单帧超限）属于运行时/取证层，由运行时修复与诊断负责，不靠「让 Agent 少输出」
的提示词兜底；任务下发只负责把范围、材料与完成标准写清楚。
