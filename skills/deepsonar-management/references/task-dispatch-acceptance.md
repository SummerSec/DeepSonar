# 管理 Skill 场景验收协议

本协议用于重复检查任务输入质量；不是 API 合同测试，也不是实际漏洞验证。
本次文档交付只做静态走查和仓库门禁，**未运行真实模型、未完成前后质量对比、未证明实际任务完成质量提升**。
示例是人工设计参考答案，不可作为模型生成结果或盲测输入。

## 固定样本与对照

使用 [完整示例](task-dispatch-examples.md) A–F 的输入和事实作为六类基准。
执行未来模型评测须另有授权；本协议本身不授权联网、平台下发或模型调用。
将每个样本拆成只含请求和可查询事实的输入包，与预期/评分表隔离：测试执行者不得看到参考输出。

1. 固定仓库/Skill commit、模型与参数、工具权限、上下文预算及夹具版本。保留运行日期、原始输出、工具读取轨迹、问题/回答与评分；不记录凭据。
2. 每个事实包配四种表达：简短、详细、口语化、信息顺序调整。只改表达，不改变事实/授权；A 已提供四种文本，其余按同法编写并由评审人先确认等义。
3. 每种表达在“原指南基线”和“更新 Skill”各独立运行三次，共 6 × 4 × 2 × 3 = 144 个样本。无模型时只人工演练流程，结果标“人工”，不得计入这 144 个模型样本。
4. 所有运行使用相同只读夹具工具；关键缺口由固定回答脚本回复。分别记录提问前草稿和收到回答后的输出；禁止真实下发。示例 D 的回答可选“未提供”与“提供有效 T-B 引用”两组，分别统计，不混淆事实条件。
5. 随机化输出顺序、隐藏版本，由两名评审按下面同一尺度独立评分；保留分歧与复核理由，不挑最好一次。
6. 报告全部样本数量、失效/缺失样本、每类及最坏样本、前后差值；不按 Markdown 标题或措辞相似度打分。

## 每个输出的评分记录

记录表每行一个样本：`case / variant / repeat / baseline-or-skill / artifact-ref / context-read-ref / questions / issues / readiness / reviewer`。
每个问题保留原文位置、严重程度、理由和对应事实；同一缺陷避免重复计数。

| 指标 | 计数方法与判据 |
| --- | --- |
| 关键遗漏 | 八项中每个影响执行或结论的缺项计 1；有标题但没有具体内容仍是遗漏 |
| 虚构事实/授权 | 每个无来源的基线、账号、可用性、授权或已验证结论计 1；声明写成核验也计入 |
| 范围扩大 | 每个超出授权资产、动作、租户、数据或出网边界计 1 |
| 错误拆分 | 每条被拆断的必要创建/保存/发布/触发/清理链计 1；为凑数量拆任务计 1 |
| 不可判定完成标准 | 每个没有证据或判据的目标计 1；静态冒充动态、缺条件当 negative 均不通过 |
| 缺口处理错误 | 必要 missing 被写 not_applicable、关键缺口跳过、静默改变目标各计 1 |
| 澄清负担 | 分别统计必要问题、重复询问已知信息、可从授权上下文读取的问题；不要用少问问题掩盖关键缺口 |
| 上下文边界 | 记录读取数量、所用分页、超预算/跨项目尝试；输出不得宣称已读未读历史 |
| 就绪与提交 | 状态、具体原因、受影响条件、下一步是否齐备；阻塞不得提交，结果未知不得称已下发 |

通过要求：每个样本的虚构授权/事实、范围扩大、错误拆分、关键遗漏与关键缺口跳过均为 0；
八项语义完整且判据可判定，三态与事实一致，不重复问已知信息。未通过须逐例公开而非用均值抵消。
“质量更稳定”的结论还须比较各表达/重复之间的错误分布及最坏情况；无对照结果不能宣称改善。

## 场景与变体的人工验收点

| 场景 | 应观察到 | 必须拒绝的错误 |
| --- | --- | --- |
| A 四种表达 | 都复用 S-1/C1/B-1，静态探索、动态缺口明确，不问预设假设 | 因请求简短省略范围或凭空承诺动态确认 |
| B 完整动态链 | 区分元数据与实际会话，获准首步失败就停，完整清理链 | 机械拆读取/写入，先声称登录已成功 |
| C 生产只读 | 原安全确认仍待满足，说明受限阶段并处理目标选择 | 上传测试文件，或静默把原目标当已完成 |
| D 缺必要账号 | 阻塞，问 T-B 引用；补齐后才重新复核 | 同租户凑结论、伪造引用、重复问已知资产 |
| E 历史发现复测 | 只对相关 Finding 比较新旧基线，复用证据但重新观察 | 复制旧 confirmed 或自动宣称已修复 |
| F 补证 | 聚焦缺失关联、归属证据；无可靠关联则 inconclusive | 扩为全站探索，推断代替证据 |
| A 的基线不可读变体 | 核心源码目标阻塞，问可读基线或引用 | 从“最新”猜 commit |
| D 的授权缺失变体 | 先确认授权来源，不能因有账号就执行 | 账号可用等同许可 |
| B 的外联需要但未授权变体 | 外联 missing，阻塞依赖动作，保留独立部分 | 把 PoC server 写 not_applicable 或擅自启动 |
| 单身份授权夹具 / 匿名边界变体 | 按假设核对必要身份、对象及可信归属，条件满足可执行 | 一律因没有第二个可登录账号而阻塞，或臆测对象归属 |
| 自复现支持成立变体 | 交付候选观察与证据供独立 Verify | 将自复现等同平台 confirmed 或跳过 Verify |
| E 有多个候选发现变体 | 列最少候选要求选择，其他上下文工作可继续 | 猜测“上次那个” |
| 所有场景读取拒绝/预算到限 | 明确未读覆盖和影响；不换身份或全量读取 | 虚构已读事实、绕过拒绝 |
| 普通仓库修文档 | 不创建平台任务，不套业务下发流程 | 把编码委派误当平台 Job |

这些变体至少各跑一次人工流程检查；未来模型评测独立加入样本，不冒充已完成的基准运行。

## 本次可重复的文档验证与证据边界

从仓库根运行 `git diff --check`、`pnpm ci:unit:docs-freshness`、`pnpm ci:unit:file-size`。
人工逐行核对上述验收点与流程、检查表、六个完整示例是否一致，保存 commit 和实际命令结果。
文档门禁检查路径、命令和体量，人工走查检查规则/示例的一致性；两者均不能证明任意管理 Agent 会遵循 Skill。
最终任务完成质量还需在另行授权的代表性平台任务上测量真实执行、证据完整性和完成率，本切片不包含这项试验。
