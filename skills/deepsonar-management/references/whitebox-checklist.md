# 白盒任务前置条件

白盒任务的前提是**能读到代码、能定位改动、能给出可复现的判据**。以下逐项确认后再下发；缺项写「缺失」，
不要用「自行获取」掩盖没有基线。

## 1. 源码与基线

| 项 | 要求 | 缺失时 |
| - | - | - |
| 来源 | 仓库地址 + 分支/tag/commit，或已上传的源码包引用 | 先补基线，不要从模糊的「最新版本」开始 |
| 可读性 | 目标模块路径明确，能被 Agent 读到 | 收窄到可读路径，或记录 `missing` |
| 版本一致性 | 基线 commit 与部署版本/依赖锁文件对齐 | 说明差异，完成标准里标注适用范围 |
| 依赖与构建 | 依赖清单、构建脚本、私有源可用性 | 记为 `missing` 并说明验证限制；静态审查可继续，动态验证标注缺少条件/无法判断，不能当作不适用 |

基线一旦确定，写进任务说明或契约的「目标与基线」；不要留给执行阶段猜。

## 2. 范围与假设

- 探索列明覆盖问题与入口，不要求预先漏洞假设；验证任务列明可检验的假设（例如「上传路径未校验扩展名」）。
- 列明**禁止动作**：不改生产配置、不打真实用户数据、不引入新外联目标。
- 允许的情况下，source→sink 的路径追踪本身就是任务目标，**不要求创建任务前就已证明漏洞存在**。
- 明确排除项：第三方依赖本体、基础设施层问题等，避免结论发散。

## 3. 静态与动态的完成标准分开写

| 验证方式 | 完成标准 | 常见误写 |
| - | - | - |
| 静态审查 | 给出 file:line、数据流路径、触发前提与对抗性输入 | 「看过相关代码」 |
| 动态验证 | 给出可复现步骤、实际响应/副作用、环境与版本 | 「应该能触发」 |
| 两者都做 | 分别写标准，并说明动态不可用时静态结论的适用边界 | 用静态结论冒充已动态验证 |

构建或动态环境不可用时：**说明验证限制**（缺什么、为什么缺、影响哪些结论），不伪造可执行条件，
也不要承诺任意目标必然产出 confirmed finding。

## 4. 证据与停止条件

- 证据要求：代码片段、请求/响应、日志、命令与退出码；大输出走运行时取证通道，不靠提示词压缩。
- 停止条件：已满足本轮证据判据、预算耗尽、遇到范围外资产、需要未授权凭据——任一触发即停并记录原因。
- 清理：不留下临时账号、后门文件、未清理的容器或外联目标。

## 5. 下发前自查（白盒）

- [ ] 仓库 + 基线（commit/tag）明确，且与实际部署版本关系说清
- [ ] 目标模块路径与范围、排除项明确
- [ ] 探索范围或验证假设明确，必要状态链未被拆成互相依赖的碎片
- [ ] 构建/测试入口可用，或已记录不可用的影响
- [ ] 静态与动态的完成标准分别可判定
- [ ] 禁止动作、停止条件、证据要求已写
- [ ] 未把凭据明文写进任务说明
