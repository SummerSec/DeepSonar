# 项目知识库实施与删改方案

> 状态：设计提案，供实施评审。2026-11-22。现状以 SummerSec/DeepSonar 主线提交 `2e491d6987285f5eaf578458ba2086bf7f3f1c60` 为基线。以下“目标”“删除”均指拟实施的变更。

## 一、产品决定

每个项目拥有一个私有知识库，库中每条记录称为“知识条目”，英文统一使用 knowledge。项目自身就是库的身份，创建项目即可使用，无需再创建一个同名资源。业务 Agent 在运行中遇到值得复用的发现，或在当前会话收尾时，主动判断是否写入。优先写项目独有的事实、容易误判的信号、反复试错后有证据支撑的短做法。无新增时照常完成任务。普通条目通过来源及权限校验即可入库，供以后任务检索。独立 Skill 仍有自己的发现、治理和授权流程。

给 Agent 的常驻指令

> **何时搜**　接续旧任务、判断取决于项目特有约定，或准备重复一次高成本排查时，先按对象和现象搜标题、标签。命中再读核心经验，必要时展开证据。常规步骤直接做。
>
> **怎么写**　运行中或收尾时发现可复用经验，先查重，有新增再写。用极其精炼的语言，一条一事，一句能说清就只写一句。标题写现象，标签用搜索词，正文写适用条件和结论，附来源。无新增就结束。
>
> **何时改**　读到冗长或难搜的条目，能保留原意和例外就当场精简、改标题或标签。使用中发现错误、过时或遗漏条件，取得依据后立即修订。
>
> **强制要求：用后必评。** 依据条目作过判断或尝试过做法，使用结束、结果明确时，必须立即调用 `record_knowledge_feedback` 评价实际使用的版本。选“有用／部分有用／无用”，后两项附一句原因。修订过也必须评原版本。收到可修正错误，按提示修正后重提。

示例标题为“归档日志按时间查为空，按请求 ID 可查”，标签为“归档日志、时间查询、空结果、时区”。核心经验可以只有两句：“该导出文件用 UTC。先用已知请求 ID 核对时间戳，再判断是否缺数据。”来源指向本次观察；核对过的版本可以写在第一句。单句足够时，省去详情。

## 二、五个 Agent 操作

名称沿用能复用的 Control API。所有项目、任务、Job 与 Attempt 身份由平台推导。读写各自受冻结的 operation allowlist 和当前授权约束。接口清单是业务 Agent 的日常操作，底层原有回执查询仍可用。

| 操作 | 核心输入与返回 | 规则 |
|---|---|---|
| 搜索 `search_project_knowledge` | 标题关键词、标签、游标 → ID、版本/hash、标题、标签 | 搜索范围限于本项目的知识条目。只匹配标题和标签；标签规范化、去重，明确传入的多个标签取交集。标题支持中文片段及错误原文，多个搜索词可分散在标题与标签。精确命中优先，以稳定键分页。建议每页默认 5 条。 |
| 读取 `read_project_knowledge` | 搜索结果的 ID、版本、hash、层级 → 核心短文或详情/来源引用，以及 usage_ref | 默认只读核心短文；选读详情时返回同一版本。证据原件仍通过原授权入口展开。同一 Attempt 重读同一版本沿用 usage_ref。读取工具描述须提醒“实际使用结束后，必须用本次 usage_ref 调用 record_knowledge_feedback 评价”。 |
| 新建 `create_project_knowledge` | 标题、至少一个标签、核心短文、来源引用、可选详情 → 条目、版本、回执 | 同项目内有效 Fact/Evidence 来源由平台验证。建议复用已有写入大小和来源数量限制，逐字段限制 UTF-8 字节，超限指出需缩短的字段。成功写入普通知识不派发模型 Job。 |
| 修订 `update_project_knowledge` | 条目、预期版本/hash、变更字段、原因、必要的新依据 → 新版本、回执 | 允许修改标题、标签、表述及结论。精简可沿用原来源；更改结论或适用条件必须说明更正并附依据。同一基线并发写入仅一次成功，其余返回当前版本供重读。 |
| 评价 `record_knowledge_feedback` | usage_ref、结果、可选原因 → 评价回执 | Agent 可见的工具描述必须写明：“使用知识条目结束后，必须调用本接口评价实际用过的版本。传入读取时的 usage_ref，选择有用、部分有用或无用；后两项附一句原因。”原因可选“表述冗长、条件缺失、已过时、结论错误”。搜索或阅读后发现不相关、内容不符合预期且未实际采用时，直接跳过，不评价、不记无用票。标题或标签有误可调用修订接口；有依据发现内容错误可修订，并附依据。Skill 继续按其自身契约校验。 |

五个接口均遵守[项目级 Agent API 错误处理原则](../../../DESIGN.md#43-失败反馈与修正)。可修正的违规请求沿现有 RepairFeedback 在本次工具响应中返回操作、错误字段、约束和重提方式。例如评价选了“部分有用”却缺原因，就提示“请在 reason 补一句哪些部分有用或需要更正，再提交评价”。拒绝不产生成功回执、票数或使用时间。读请求改正参数后重发；写请求修改内容后按契约用新的修订及幂等键提交。响应丢失时先按原键查回执；未知效果不得自动重放。

搜索按需发起，不把目录放进启动提示。建议正文一两句，服务端只校验结构、来源和体积，避免为检查“是否精炼”再调用模型。写入回执和搜索条目均不复制整段来源。知识内容当作项目资料展示，不能据此获得新权限或改变任务完成判据。

## 三、评价、使用与淘汰

| 项目配置 | 平台默认值 | 生效语义 |
|---|---:|---|
| 闲置下架天数 | **365 天** | 连续达到该时长没有确认使用，即具备下架条件。 |
| 无用下架次数 | **5 次** | 同一结论累计达到阈值的独立任务数，不要求连续。有效的第五次即可触发。 |
| 下架后的删除宽限期 | **建议首版 30 天** | 这是实施建议。按下架时间起算。首版只把用户确定的前两项开放为项目覆盖。 |

项目设置页展示“当前生效值”和“继承平台默认／项目覆盖”，只允许项目管理权限修改。接受正整数，清空覆盖恢复继承。保存时显示按新阈值预计命中的在架条数，保存配置和审计后在下一次清理按新值处理。阈值调宽不自动恢复既有下架项。

- **强制评价与任务执行。** Agent 须在原 Job 有效期间履行用后必评要求。评价被拒时，提示直接返回当前调用者，Agent 在原授权和预算内修正并重提，可同时推进其他业务步骤。Scheduler 按既有业务条件处理 `mark_job_done`，不因缺评或知识接口报错暂停任务、要求重交完成请求或转人工。只有接受的评价才计票；到任务结束仍无评价回执的读取保留“未反馈，效果未知”。仅搜索或打开后未采用无需评价。开放读取时须同时提供反馈操作；版本后来下架或撤销时可对原 usage_ref 评价，无须重读正文。
- **使用口径。** 读取产生精确版本的 usage_ref；提交三种实际使用评价之一即确认使用。平台用首次接受该任务评价的服务端时间更新最后使用时间。未反馈的读取作为“效果未知”单列；搜索、预览、详情展开、润色、重复投递和后台检查均不续期。没有确认使用时从首次上架算。该定义衡量可观察的使用，沉默不代表模型已掌握。
- **计票。** 以项目、条目、结论代次、根业务任务去重。并行子 Job、换 Attempt 和传输重试合计至多一票；绑定真实 usage、当前执行身份及被读版本。作者所在的根任务和知识治理、评测用 Job 排除出淘汰计数，正常业务验证任务仍可评价。三种评价保留明细，不计算星级；“不够精炼”可以与“有用”并存。相反意见可在不同任务形成多条记录，点赞不抵消已发生的无用票。
- **版本。** 每次写入产生新版本。润色、改标题或标签沿用同一结论代次和票数；有依据的实质纠错进入新代次，旧票可追溯。旧版本迟到评价只归属其代次。普通编辑不刷新闲置时间。实质变更需显式注明是纠正哪条结论及对应来源，不能仅靠换标题清票。
- **状态。** 任一阈值满足即由 Scheduler 将在架条目标为下架，记录原因、阈值、时间及版本，从新搜索和新 Job 目录移除。宽限期内项目管理员可基于纠错或明确复用需要恢复并记录依据。恢复时设定新的闲置起点；因无用票下架的须先形成实质修订，不能恢复后仍携原票反复上下架。安全撤销优先，并禁止通过普通恢复重启授权。
- **删除的含义。** 宽限期满，删除知识库展示正文、索引和可恢复入口，保留最小删除标记、版本标识和不可变回执。历史 Job、证据、授权快照或其他对象仍引用的版本字节只能保留在受控历史路径；仅无保留义务且无引用的正文进入物理回收。对已有活动 Job 按冻结版本和实时授权读取，直到其引用释放；安全撤销即时拒读。不能从知识库删除一篇经验就级联删除原始证据。
- **调度与并发。** 差评入账时在事务内按当前版本重算阈值。闲置处理、配置调整和到期清除复用 Scheduler 的持久唤醒与有界分批扫描，以数据库时间计算；锁内复核最新配置、使用、引用和状态。评价、修订、删除并发时按锁序串行，重启或重复领取不重复下架/删除。操作员可在项目知识页查看下架原因并在宽限期内恢复。

## 四、数据与实现落点

1. **复用项目和知识实体。** 继续使用 PostgreSQL 的 `project_knowledge_items`、`project_knowledge_versions`、`project_knowledge_usages` 和 `project_knowledge_receipts`。已有 `title`、`keywords_json`、`active_version_id`、`generation` 和不可变版本。知识条目的标签与短文/详情要随版本冻结；当前索引投影同事务切换。项目设置只持久化覆盖值。知识编辑版本与结论代次分开，以支持润色不清票。
2. **补足生命周期数据。** 持久化首次上架、最后确认使用、下架原因与时间、删除标记和当前结论代次。反馈记录须能关联精确 usage、根任务和代次，有数据库唯一约束防重复计票。最后使用时间、计数都是可由已接受事实核查的投影。下架状态复用现有 `retired`，删除标记仅用于经验，不重解释 Skill 的状态。普通去重写入、事件、状态和回执共用事务。
3. **沿用可信执行入口。** 改 shared-types 的 Zod 契约、Control operation 注册、宿主 handler、事务应用层和运行时发现指引；用现有 CAS、hash、幂等键和 RepairFeedback。写入目标限于本项目知识库。创建校验来源，编辑校验可引用版本及来源，详情读取实时复核撤销。模型只提交提案，由 Scheduler 执行写入。旧 Job 不新增写权限。
4. **目录与规模。** 当前目录冻结知识条目和 Skill 的版本元数据，有 1,000 项保护；模型启动不会因此收到全目录。首版沿用冻结边界和现有硬限，搜索在授权集合内进行，监测项目目录规模。若需要突破上限，应独立设计可分页的快照；单纯提高上限会把成本移到 Job 创建时。
5. **存量口径。** 先只读清点 active/draft/stale/retired/revoked、无标签条目、在途 work、旧反馈、共享 blob 和历史引用。已有符合新契约的在架经验复用原身份；缺标签等不合规项列入待整理，不向 Agent 发布，项目管理者可按新契约显式修订。旧反馈 `failure` 不能回填为新规则的无用票。存量缺乏可证明的使用起点时，以新规则启用日开始 365 天计时，避免上线即误删。切换记录起点和统计口径；不得改写历史 Job 快照或给旧版本伪造评价。

## 六、交付顺序与验收

| 顺序 | 交付内容 | 可以判定完成的条件 |
