# 0020 成功业务 Job 由 Scheduler 登记有界知识整理

> 状态：**被 [0021](0021-knowledge-source-preview.md) 取代**（2026-11-09 用户将范围收敛为成功来源登记与只读历史预览）。
> 同步日期：2026-11-09

## 背景

原有首次整理只能由正在运行的 Agent 调用 `request_project_knowledge`。实际平台有已成功且产出结构化 Fact 的任务，但知识 work、proposal、receipt 均为空；仅有发现 Skill 的可选提示不能保证任务收尾进入整理。

## 决策

Scheduler 在业务 Job 与 Attempt 成功结算时登记现有知识 work，固定绑定来源Job并复用已有链。它只安排候选整理，不能替 Agent 决定知识正文、评测结果或激活。首次请求的来源从“只由当前Agent请求”扩展为“Agent请求或Scheduler验证成功来源后登记”；[0003](0003-api-only-control.md) 的Agent只提案与API-only控制边界不变。

登记在主终态事务的独立savepoint内完成，CAS输入异步准备，失败不回滚业务结果。输入权限继续受来源Job冻结allowlist、精确来源归属与治理版本约束。Hub、Report、知识治理Job及其trial不递归触发。空来源保留可查询的跳过记录，终态失败、未知效果、撤权或归档不得被补做转成可执行来源。

历史补做是项目管理操作，按精确来源Job和同一幂等键登记，不重启旧Job、不恢复终态token、不新建模型执行者。maker、trial、evaluator、reviewer、累计预算和最终激活全部复用现有知识治理流程。

## 后果与验收

成功任务现在会产生额外的候选整理与模型调用，继续受原有知识预算与项目调度并发约束；无来源不调用模型。整理可能拒绝、阻塞或无新增知识，不能用Job成功或队列建立冒充知识质量。

数据库行为回归覆盖重复/并发、自己的来源、未知效果、空来源、递归隔离、savepoint失败与异步准备；管理回归覆盖项目权限、批量上限与跨项目整批拒绝。测试仅在GitHub Actions执行，真实模型产出与收益仍按独立证据记录。

## 替代方案

- 只加强发现Skill提示：仍依赖模型记得主动请求，无法提供确定的收尾触发。
- 直接把任务日志写成active Skill：绕过来源、独立评测和审查，拒绝采用。
- 管理者重用历史token调用Control：破坏终态和Attempt fencing，拒绝采用。
