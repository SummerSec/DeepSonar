# 0024. 从持久工作历史推导项目知识合批、间隔与连续无产出停发

> 状态：**已采纳**；本轮目标契约，最终 SHA 的 GitHub Actions 验收另计，不表示已部署。
> 决策日期：2026-11-16
> 同步日期：2026-11-16
> 来源：用户明确授权修复自动项目整理；`collector`、[knowledge-wake](../../../apps/scheduler/src/knowledge-wake.ts)、[activity](../../../apps/scheduler/src/domains/project-knowledge/activity.ts)。
> 关联需求：FR-KNOW-001、NFR-UX-001。

## 背景

[0023](0023-project-knowledge-collection.md) 已采纳持久来源审计、有界项目批次和独立评测。其每批最多 4 个来源及仅按项目繁忙等待的准入，不能限制少量来源频繁触发、连续无产出仍持续派发的模型成本。本轮要求按项目积累、限制自动批次频率，并在连续无产出时停止新批次；重启不得恢复派发或重置失败历史。下述 4 来源、24 小时、连续 2 次及扫描 32 来源等数值阈值为本轮实现取舍，不追认为用户逐字指定参数。

## 决策

1. 本决定替代 0023 决策第 2 条的来源数量和自动准入规则，并扩展第 3、7 条的事务重验及可见性；0023 的历史决定段保留。来源登记继续即时持久化，项目至少积累 4 个未处理来源，或最老待处理来源等待满 24 小时，才满足来源门槛；同时距上次自动批次创建须满 24 小时。项目已有非旧自动 `pending/running` work 时不准入新自动批次，不新增约束全部显式请求的唯一索引。
2. 每次有界扫描最多 32 个候选来源，合并其中可容纳者；manifest 仍最多 19 个原始 inputs 及一个可选冻结 governor。仅因本批剩余容量不足的来源必须保留待处理，不写 collected/skipped，也不得在第一个放不下的来源处停止扫描。单个来源本身超过硬限制仍按原永久拒绝处理。
3. 自动批次仅指当前 `knowledge:project:` 工作。成功必须是 work `completed` 且关联提案有 `active/retired` 产出；`blocked/cancelled`，以及 completed 但无该产出的自动批次均计无产出。连续 2 个自动批次无产出后必须停发新自动批次，待处理来源和已有 work 历史保留。成功自动批次或成功的显式知识整理可截断失败链；失败的显式整理不增加或清除自动失败计数。显式成功沿用相同 completed 与提案产出口径，不新增恢复按钮或隐含权限。
4. 连续失败、最近自动批次时间与是否恢复，必须从项目持久 `project_knowledge_work` 及关联 proposal 历史推导，不新增表、持久计数、配置开关或进程内重置逻辑。重启、时间流逝和治理 hash 变化均不得清零；治理变更仍按原规则阻断旧 work，不改写旧记录或预算。旧 `knowledge:auto:` work 不充当新批次或恢复成功，不恢复自动推进。
5. collector 选项目、CAS 准备后的项目行锁事务重验、durable wake 及 activity 必须共用同一数据库准入规则。事务内重新检查来源门槛、间隔、连续失败与繁忙状态，以及原权限、最新 Attempt、来源/hash、未结算效果、重试代次及 governor。不得用 CAS 准备前的 ready 状态越过新出现的停发、冷却或繁忙；work 和逐来源 collected 审计仍原子提交。wake 计算同时尊重项目门槛、批次间隔和来源 retry 的未来时间，繁忙或停发项目不产生立即过期的采集 wake，不新增轮询执行器。
6. 原 activity 响应新增 `collection:{state,pending_sources,consecutive_failures,next_collection_at}`，state 限于 `idle|busy|accumulating|cooldown|ready|halted`。它是只读调度投影，不是新持久生命周期；与 summary 分别查询，并发及异常损坏数据不保证计数同值或同一快照。accumulating 可表示来源积累或 retry 等待，cooldown 仅表示自动批次间隔为最后限制，下次时间始终尊重 retry。现有知识页展示积累、冷却、执行中、停发及下次可准入时间；无新增通知、开关、恢复按钮或轮询。完整字段口径由[项目知识专题](../../PROJECT_KNOWLEDGE.md#积累与复用可见性)维护。

## 本轮评审修正（2026-11-16）

评审发现原 feedback.ts 对每条 usage 反馈直接 enqueue work，可绕过项目 collector 的积累、间隔及停发门。本轮决定补充：`record_knowledge_feedback` 仅持久化已接受的 usage 反馈，操作结果为 `{usage_ref,state:"recorded"}`，不返回 `work_ref`，也不入队或启动知识 work。成功业务 Job 的已接受反馈经普通来源登记进入项目 collector，冻结精确 usage/反馈、target 版本/hash 基线及 evidence refs；同样受 4 来源或等待 24 小时、自动批次间隔 24 小时和连续两批无产出停发约束。原 Job 没有冻结 `request_project_knowledge` 权限时，不因提交反馈获得自动整理权限。显式 `request_project_knowledge` 仍按原有授权、来源、预算与幂等约束请求整理，不被自动策略替代；不得把仅反馈记录当作显式整理。反馈记录不构成 active/retired 产出，也不重置连续失败；usage/反馈数、源 Job 登记、批次采集及知识生效保持分层。精确输入须满足原项目、版本撤销和 evidence 读取权限，并占用原有界 manifest，不另建反馈自动通道。旧 work、已持久回执和预算保留；新反馈结果不提供 work_ref 兼容返回。

本修正追加到本轮决定，既有历史 ADR 决定段不改写；实现按上述目标整合，最终 SHA Actions 待验，不宣称生产已部署。Actions 应覆盖 feedback-only 成功来源、recorded 无新 work、精确反馈/基线/证据冻结、自动准入不可绕过、原权限不扩展与显式请求保持独立。

同源显式 work 的输入快照不改写；其冻结后收到的 usage 反馈不能被 existing_work 永久排除，须等项目在途工作结算后按相同准入规则进入批次。反馈事务重验对整个批次先按 id 顺序锁 usage、再锁全部 version、最后锁 item，避免逐来源持有 item 后再等待另一 version，与版本撤销的 version→item 锁序构成死锁环；精确 grant 和撤销检查保留。

## 状态

2026-11-16：在用户授权修复自动整理的范围内采纳上述实现取舍；文档与并行代码修改在共享工作树整合，不能由决策采纳推定实现或验收通过。最终 SHA 的全部适用 Actions 仍须实际核对；本轮不部署、不重跑历史生产任务、不执行真实模型收益试验。

## 后果

- 正面：减少低密度整理和连续无产出的重复模型工作，使用已有知识页说明等待或停发原因，不增加人工逐批审批。
- 代价：小量来源最多等待门槛时间，冷却与 retry 还可进一步推迟执行；停发保留未处理来源，成功显式整理后才可能恢复，恢复仍受其他准入门约束。减少成本与注意力收益是设计目的，尚无实测结论。
- 保留：来源审计、旧任务/快照/回执、累计 32 Jobs/1800 秒/2 次候选修订、最小 Job 预算拦截、完整独立评测/审查和未知效果对账不变，不提高预算掩盖失败，不承诺模型质量收益。
- 验收：Actions 中覆盖 4 来源或 24 小时、批次间隔、32 候选装箱及保留、跨项目隔离、两次无产出停发、跨重启与治理变更不恢复、成功显式整理恢复、CAS 期间准入变化、未知提交去重、未来 retry 不热循环，以及 activity/Web 投影。测试/build/typecheck 仅在 Actions 执行，文档静态检查不替代工程验收。

## 替代方案

以下为本次分析，不追认为历史讨论：

- 仅隐藏知识任务：不能减少真实执行成本。
- 进程内失败计数或按时间/hash 自动恢复：重启或配置变化会绕过持久停发约束。
- 无限扩大 manifest 或按队首放不下即结束：前者破坏输入上界，后者遗漏本次候选中仍可容纳的来源。
- 增加停发表、开关和恢复按钮：已有 work/proposal 历史及显式整理可表达本轮规则，无需第二份状态或权限通道。
